How a room actually gets written. Matt dictates a long note about one area, hands over that room's reference manuals, and a model authors the pages from the dictation using these four pages plus templates/. The worksheets below are the prompts for the dictation — not a form anybody fills in by hand.

The Three Page Shapes

Every page on this site is one of three shapes. Pick the shape before writing a word — it decides the template, the ordering rule, and when the page is done.

ShapeUse it whenOrdered byTemplate
ProcedureThere is one right order and the operator is standing there doing itTime — step 1 happens firststartup-step.html
DiagnoseSomething is already wrong and the operator needs the fastest path to a causeLikelihood × speed-to-checksymptom.html
ReferenceThe answer is a lookup — a number, a destination, a stateThe room's own order (IN 13 before IN 34)subpage-view.html

Procedure

Numbered steps, each with a where line naming the device so the operator can find it without reading the step first. Actions lead with the verb. A caveat goes in a .note block, never in a qualifying paragraph before the step.

Worked example: Toronto East · Video · Startup Procedure — five steps, each one physically doable in order, ending in a verify step. A procedure without a verify step isn't finished.

Diagnose

Accordions, one per symptom, with the summary written the way the operator would say it out loud — "Main Screen black / frozen / wrong source," not "PGM output anomaly." Inside: the fastest check first, then the next most likely cause, then the escalation or cross-link.

Worked example: Toronto East · Video · Diagnose a Symptom — nine accordions, each tagged with the lane it lives on so the reader can skip six of them immediately.

The tag trick generalizes. Video tags each symptom Lane A or Lane B because that one question halves the search. Every discipline has an equivalent split worth finding — ask for it during capture.

Reference

A table, in the room's own order. Include the "not filled in" rows rather than omitting them — a visible gap is a task; a missing row is a lie.

Worked example: Toronto East · Video · Output Cross-Points, where three rows read not filled in, and Unverified / Gaps, which exists only to hold them. That page shrinks as gaps close; when it's empty, it goes.

When a page fits none of them

It's two pages. The usual tell is a page that starts as a procedure and turns into a table halfway down — split at the seam and cross-link.

Capture Worksheets

The questions to ask a room. Take one into the booth, get the answers however you like — dictation is the expected form — and hand them to a model with the room's manuals.

Ask for specifics, not summaries. "We recall a saved state" is not an answer. "PROFILE, right arrow, knob to 44, RESTORE" is. If an answer could be true of any room in the country, it isn't captured yet.

Every discipline — ask these first

  1. Power order. What gets switched on, in what order, and what has no power switch at all?
  2. The saved state. What's the "start here" configuration, where is it saved, and exactly which buttons recall it?
  3. The shared-venue split. What's ours, what's the venue's, and what has to be handed back after?
  4. The verify step. How does the operator know startup worked before the service starts?
  5. The top five Sunday failures, in the operator's own words, each with the fix.
  6. The vocabulary. Which words does this room use to mean something non-obvious?

Video Engineering

  • Switcher and router models; where saved states live and how they're recalled.
  • What each M/E is for, and where each one routes.
  • Keyer assignments — which key, what type, what content, when it's up.
  • Input cross-points: every physical source, its label, and where it lands.
  • Output cross-points: every destination, its device, and its source.
  • Which destinations bypass the switcher entirely — the direct-crosspoint lane.
  • Sunday run of show: expected bus state at each point in the service.
  • Any output whose source nobody has written down. These become the gaps page.

Audio

  • Console model, show file name, and the recall steps.
  • Patch sheet / input list; where every stage source lands.
  • Gain structure notes — anything set once that nobody should touch.
  • Wireless frequencies and the battery routine.
  • IEM mix assignments — who's on which mix.
  • The hand-off to video: which audio paths feed the broadcast or capture chain.

Lighting

  • Console model, show file, and power order.
  • The rig split — ours versus the venue's, fixture by fixture if it matters.
  • Universes, addresses, fixture schedule.
  • Service looks and their trigger points — which look, fired when, by whose call.
  • House light control: what controls it, and who's allowed to.
  • The hand-back routine — what state the venue expects the rig left in.

Cameras

  • Models and counts.
  • Per-camera build: lens, paint, frame rate, SDI return.
  • Positions, and the shot vocabulary exactly as the director calls it.
  • Tally source and comms channels — who hears whom.
  • Any camera with a fixed job that constrains the switcher (a locked capture source, for instance).
Not every campus has every seat. Toronto East has no camera desk, and that's a decision, not a gap. Record which seats a campus genuinely doesn't have, so nobody scaffolds one out of symmetry.

Writing Rules

The voice, in six rules. They exist to settle arguments quickly, so apply them literally.

1. Write for pros

This site documents this room, not the craft. Never explain what an M/E, a crosspoint, a DMX universe, or a gain stage is — the reader already knows. If a draft starts teaching fundamentals, cut it.

2. Expand knowledge; don't script behaviour

A page should leave the operator understanding the system better than a button sequence would. Include enough why that they can improvise when reality differs, and point at the source manual. Never a bare press-this-then-that script.

These two rules are not in tension: don't teach the craft, do deepen understanding of this room.

3. Lead with the action

"Press PROFILE, then the right arrow." Never "In order to restore the profile, you will want to…".

4. No qualifying paragraphs

Context goes in a .note block or it gets cut. If a page opens with two sentences of throat-clearing before the first useful fact, delete them.

5. Use the room's vocabulary, exactly

Write the word the team says, then define it once where it first appears. At Toronto East "Resolume" means ME4, "Uplink" is the broadcast join on Resi, and macros are either River's or Elevation's. Another campus will have its own list — capture it rather than importing this one.

6. Mark up consistently

Readability wins every tie. This site has already rejected light font weights and small reading sizes twice. If a stylistic choice and legibility at the desk disagree, legibility wins — and that decision doesn't need re-litigating.

Blank-Campus Kit

Scaffold a campus that doesn't exist yet. Follow these seven steps in order and the new campus appears in the launcher, the rail, and the tab bar with no other file touched.

Before you start, you need two things: the campus's short code (three letters, permanent — it's in every URL forever) and the list of seats that campus actually has. Don't invent a seat for symmetry.
1

Register the Campus in the Shell

assets/app.js · the CAMPUS map, near the top
  1. Add one entry: the code as the key, with label (full name, shown in the rail), short, and discs — the seat list, in the order you want the rail to show them.
  2. List only real seats. The campus's tab bar and rail are built from this array.
2

Create the Folders

Repo root
  1. One folder per seat: <code>/video/, <code>/audio/, and so on.
  2. Nothing else goes in them. Assets stay shared at the root.
3

Copy a Hub Page per Seat

<code>/<seat>/index.html
  1. Copy an existing scaffold hub from another campus — the same seat if it exists, so the card titles carry over.
  2. Set the <html> tag: data-depth="2", data-campus="<code>", data-disc="<seat>". That's the only per-file wiring a page needs.
  3. Update the <title> to name the new campus.
  4. Rewrite the scaffold note for this room. Never leave another campus's note in place — it names another room's gear.
Do not copy content pages. A scaffold hub is a promise of structure; a copied procedure is a wrong answer with confident formatting.
4

Add the NAV Rows

assets/app.js · the NAV array
  1. One row per page, each with campus, disc, file (full path from the repo root), hash, and label.
  2. First row of each seat is the Overview, pointing at the hub's own hash.
  3. Every page that doesn't exist yet gets pending: true and points at the hub. Flip it to a real hash the day the page ships.
5

Add the Launcher Group

index.html · the campus groups
  1. Copy an existing <div class="campus-group"> block, set its overline to the campus name and seat count.
  2. One .disc-card per seat, each with a Scaffold chip and its planned page count.
6

Verify Before Capture

A local server at the repo root
  1. Run python3 -m http.server 8000 and open the launcher.
  2. Click into every new seat. The rail must show only this campus's seats; the tab bar too.
  3. Check a narrow window, around 390px — tab bar appears, nothing scrolls sideways.
  4. Confirm no page links into another campus. Rooms never cross-link across campuses; only the playbook is shared.
7

Capture, One Seat at a Time

The capture worksheets
  1. Take the worksheet for one seat into that room. Get the answers plus the room's manuals.
  2. Author the pages from the dictation, using templates/ verbatim and the three shapes.
  3. Ship the seat, then move to the next one. Don't half-fill four seats.

A seat is done when

  • Every hub card links to a real page — no pending placeholders left.
  • Its Diagnose a Symptom page exists. A room with no diagnose page is a room nobody can fix under pressure.
  • Its rail rows have dropped pending.
  • Its card on the launcher reads Live, with an accurate page count.
Shared facts stay duplicated until proven shared. When two campuses genuinely do something identically, it can move here and both link to it. Until then, write it twice. A shared page that quietly diverges from one room's reality is worse than two honest copies.
